首次 3 秒接收观察获得 `0x2A5 / 0x2A6 / 0x2A7 / 0x2A9` 各 20 帧，`0x2A1` 27 帧，另有各关节驱动及法兰位姿反馈。该次测试未发送 CAN 查询或运动帧。

## 后续诊断：固件已确认

用户已确认绿色指示灯、原装 USB-CAN、H/L 连线，并完成 USB 重插和机械臂电源重启。适配器静默内部回环获得发送 echo 与接收帧，测试数据未发到机械臂总线。

恢复后一次 8.47 秒接收窗口记录 2,091 帧、0 个 CAN 错误帧，包含七轴、法兰位姿、状态、驱动反馈，以及 `0x4AF` 固件回复：**1.11**。使用 SDK `resolve_firmware_profile` 验证为 **v111**。证据保存为 `outputs/deployment/after-power-cycle.json`。

随后采集发现反馈仍不能持续，固件信息也并非每次都能回复。保留适配器 ACK、单次连接、USB endpoint 清理和再次重启后的 20 秒窗口，均不足以确认持续反馈；窗口末尾数据已过期，工具正确返回 `passed=false`。目前不能将接口关闭作为唯一原因。

官方 NERO API 文档确认：1.11 的正常模式需在电机使能后开启 CAN 推送，禁用状态下控制/配置命令不生效。本次任务完成环境部署、固件识别和诊断工具准备；未执行电机使能、模式切换或运动。后续持续通信验收涉及独立的真机配置步骤。

读取工具已改为固件查询与 SDK 解码共用一个 USB 会话；七轴与位姿必须完整且最近 1 秒内更新，未知电机使能状态输出 `null`。相关 13 项测试通过，另通过 Ruff 与 Git diff 格式检查。
